RetailOS Lite

AI-native retail execution system. Async YOLO shelf analysis, multi-signal fraud detection, governed outlet master data, RAG-grounded supervisor assistant, offline-first rep workflow, and full LGTM observability — built in a 72-hour sprint with production-shaped boundaries throughout.

View on GitHub ↗

Overview

RetailOS Lite is a complete field rep → AI analysis → supervisor decision pipeline for retail execution. A rep checks in at an outlet with GPS, uploads a shelf image, and the system handles everything else asynchronously: YOLO detects products and competitors, OpenAI reasons about POSM and shelf quality, deterministic rules produce inspectable compliance scores, and fraud checks flag suspicious submissions — all before the supervisor opens the dashboard.

The interesting engineering is not any single feature — it's how nine subsystems (visit workflow, async queue, AI service, fraud engine, outlet governance, RAG assistant, offline sync, observability, and RBAC) compose into a coherent product with production-shaped boundaries: every heavy operation is async, every flagged visit is explainable, and every service boundary is independently deployable.

Engineering Highlights

Async AI Pipeline — Worker-Owned Analysis

The Problem: YOLO inference + OpenAI vision + compliance scoring + report generation can take 10–30 seconds. Running that in a Next.js request handler blocks the rep, risks timeouts, and makes the system brittle under concurrent visits.

The Fix: Visit submission returns immediately with status ANALYZING. A BullMQ worker consumes analyze_visit jobs, orchestrates fraud checks → AI service call → result persistence → report generation → vector indexing as a durable pipeline. Failed jobs retry with backoff and land in a DLQ with admin replay via CLI or API. The worker exposes Prometheus counters and histograms per stage — job duration, YOLO latency, LLM latency, failure count — so queue health is measurable, not guessed.

Multi-Signal Fraud Detection

The Problem: Field reps can reuse old photos, submit from the wrong location, backdate timestamps, or strip EXIF and re-upload. No single check catches all of it, and overzealous detection creates false positives that erode trust.

The Fix: Five independent fraud signals, each with calibrated severity and explicit reasons:

  • Exact duplicate — SHA-256 hash match against all prior images (severity: HIGH)
  • Perceptual duplicate — dHash with Hamming distance thresholds (HIGH ≤4, MEDIUM ≤8)
  • GPS mismatch — Haversine distance between check-in and outlet coordinates (configurable threshold, default 200m)
  • Timestamp anomaly — future-dated or delayed client timestamps (configurable threshold, default 6h)
  • EXIF analysis — embedded GPS and capture-time cross-checked against visit metadata; missing EXIF is not penalized

Fraud runs before AI analysis in the worker pipeline — if the image is a known duplicate, there's no reason to burn GPU or LLM credits analyzing it again. Dashboard risk status is derived from signal severity and compliance score, not from a black-box model.

Outlet Governance — Not Simple CRUD

The Problem: Reps type shop names quickly and inconsistently. Naïve create-on-submit produces duplicates fast: "Rahim Store", "Rahim's Store", "Rahim Stroe" become three separate outlets with fragmented visit history.

The Fix: A matching pipeline with DB-assisted prefiltering (pg_trgm similarity + bounding-box geo), weighted name/geo scoring (0.6/0.4), and three-tier resolution:

  • Auto-match — confidence ≥0.9 within 75m with sufficient margin → link to existing outlet + create alias
  • Review queue — mid-confidence → supervisor approves, rejects, or merges
  • New outlet — low confidence → create as UNVERIFIED, await supervisor verification

Duplicate merge is not deletion: visits are retargeted, report text is updated, aliases are copied, and affected Pinecone vectors are reindexed — preserving full reporting history across the canonical outlet.

RAG Assistant — Exact Context Before Vector Search

The Problem: "Which outlets have fraud signals?" is a list question. Vector similarity search can return visually similar reports, but it can't reliably produce an exact compliance/fraud list. Standard RAG would hallucinate or omit entries.

The Fix: The assistant uses a two-tier retrieval strategy. Operational questions (fraud lists, compliance failures, POSM gaps) are answered from exact Prisma queries against VisitReport + joined visit/outlet/AI/fraud data. Narrative questions ("summarize recurring shelf issues") use Pinecone semantic search over embedded visit reports. The LLM receives both contexts with explicit rules: prefer exact data for lists, use vector matches for patterns. Every answer includes citations with visit IDs and outlet names.

YOLO + LLM — Right Model for Each Job

The Problem: YOLO can't detect POSM (it wasn't trained on it). LLMs can't reliably count products in dense shelves. Using one model for everything produces bad results and is hard to debug.

The Fix: A strict model-per-task boundary. YOLO (custom-trained, 1280px inference) handles product counts, competitor detection, share-of-shelf metrics, and overlay generation. OpenAI vision handles POSM reasoning, shelf quality assessment, and supervisor summaries. Compliance scoring is deterministic — starts at 100, applies rule-based penalties — so scores are inspectable and stable across runs. If OpenAI fails, analysis still succeeds on YOLO-only with a warning, not a crash.

Inference is routable: RETAILOS_YOLO_BACKEND switches between local CPU and Modal GPU with automatic local fallback on Modal failure.

Offline-First Rep Workflow

The Problem: Field reps visit shops with unreliable mobile connectivity. If the app requires a live connection to submit, visits are lost or reps have to re-enter data later.

The Fix: Visit drafts and shelf image blobs are persisted to IndexedDB with client-generated IDs. TanStack Query persistence keeps the mutation queue durable across tab switches and browser restarts. When connectivity returns, the queue drains automatically: image upload first, visit submission second, analysis enqueue third. Idempotency keys prevent duplicate visits from retried uploads.

Observability — Four Layers Deep

The Problem: An async system with queues, workers, and external AI services has many failure modes. "The visit is stuck at ANALYZING" is useless without stage-level visibility.

The Fix: Four complementary observability layers:

  • EventLog — product-native audit timeline (VISIT_SUBMITTED → ANALYZE_VISIT_QUEUED → FRAUD_CHECKS_COMPLETED → ANALYZE_VISIT_COMPLETED) with correlation IDs, stage, and latency per event
  • Prometheus metrics — three scrape targets (web, worker, AI service) tracking queue depth, job duration histograms, YOLO/LLM/Pinecone latency, fraud signal counts, and rate-limit events
  • LGTM stack — Grafana + Loki + Tempo + Prometheus with provisioned dashboards, Promtail log shipping, and trace propagation
  • Sentry — error capture across all three services with environment/release tagging and conservative trace sampling

The /supervisor/ops page surfaces queue health, failed jobs, per-stage latency chips, and collapsible processing timelines — all from EventLog and BullMQ directly, no Grafana dependency required.

Production Hardening Sprint

The Problem: A 72-hour sprint produces working features but leaves security and operational gaps. How do you harden without changing the product flow?

The Fix: A focused hardening slice implemented on top of the sprint codebase:

  • Auth — optional Google OAuth (allowlist-only, no arbitrary user creation) alongside credentials auth
  • Rate limiting — Redis-backed fixed-window throttling on assistant, upload, visit creation, outlet search, and AI service endpoints; 429 responses include Retry-After
  • Upload hardening — S3/MinIO pre-signed PUTs with completion verification; credentials never reach the frontend
  • Database pooling — split Prisma DATABASE_URL / DATABASE_DIRECT_URL for PgBouncer/Accelerate
  • Queue recovery — DLQ replay CLI and admin API with dry-run default and --execute confirmation

Runtime Model

  • Visit Submission: GPS check-in, outlet resolution, shelf image upload, immediate ANALYZING status. Rep never waits for AI.
  • Worker Pipeline: BullMQ durable jobs with retries, DLQ, per-stage metrics. Pipeline: fraud checks → YOLO → OpenAI POSM → compliance scoring → report generation → vector indexing.
  • AI Service: FastAPI with routable YOLO backend (local/Modal GPU), OpenAI vision for POSM, deterministic compliance rules, overlay generation. API-key protected outside dev.
  • Fraud Engine: Five independent signals with calibrated severity. Runs before AI to short-circuit expensive analysis on known duplicates.
  • Outlet Governance: pg_trgm-assisted matching, weighted name/geo scoring, three-tier resolution (auto-match / review / new), non-destructive duplicate merge with Pinecone reindex.
  • RAG Assistant: Exact Prisma context for operational queries, Pinecone semantic search for pattern queries, structured JSON answers with citations.
  • Offline Sync: IndexedDB + TanStack Query persistence with idempotency keys. Auto-drain on reconnect.
  • Observability: EventLog timeline, three Prometheus targets, Grafana LGTM stack, Sentry across all services, ops dashboard with no Grafana dependency.
